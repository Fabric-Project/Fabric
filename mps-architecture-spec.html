1Who owns a command buffer, who commits it

RULE A command buffer is committed exactly once, by whoever created it.

Not by any code the buffer merely gets passed through. Fabric's shared per-frame buffer is created once by Satin's Renderer.preDraw() and committed once by that same layer, after every node has finished encoding. A node that creates its own dedicated buffer owns that buffer's commit — nothing else does.

RULE A Fabric node must never call .commit() on a raw MTLCommandBuffer itself.

Not on the shared buffer (not this node's to commit) and not even on a dedicated buffer it created (see §2 — MPSGraphExecutable.encode(to:) can commit that buffer out from under you first). Committing is something the MPS package does internally, through its own MPSCommandBuffer wrapper, when the node explicitly asks it to.

2The crash this caused, and the actual fix

Real crash, from the synchronous branch of MediaPipeFaceDetectionNode.detect():

#6 -[_MTLCommandBuffer addCompletedHandler:] (assertion) #7 -[CaptureMTLCommandBuffer _preCommitWithIndex:] #8 -[CaptureMTLCommandBuffer commit] #11 MediaPipeFaceDetectionNode.detect(...) — targetBuffer.commit()

That signature — an assertion inside Metal's own commit bookkeeping — means targetBuffer was already committed by the time our explicit .commit() ran. The only thing that ran between creating the buffer and that call was model.encode(...), i.e. MPSGraphExecutable.encode(to:). Conclusion, confirmed by the crash itself: that call can commit the buffer internally via its own commitAndContinue, on its own — a node holding the original raw buffer reference has no way to know this happened.

The fix Every run() / submit() / encode() now takes an explicit commit: Bool. The decision stays caller-controlled — exactly the principle we agreed on. But the act of committing, when requested, happens inside the package using the MPSCommandBuffer wrapper it already built for the call — the only object that actually knows whether the buffer already changed underneath it. A Fabric node never touches .commit() directly again. 
// package-internal, not node code
let mpsCommandBuffer = MPSCommandBuffer(commandBuffer: commandBuffer)
_ = self.executable.encode(to: mpsCommandBuffer, ...)
if commit {
    mpsCommandBuffer.commit()   // the wrapper, never the raw buffer
}

3What every MPS SPM package must expose

run(inputBuffer:)

  • Fully synchronous, CPU readback
  • throws — validates buffer size before touching the GPU
  • Blocks for a free slot (already synchronous, so a brief block costs nothing extra)

submit(..., commit:, completion:)

  • Async, CPU-readback via completion
  • throws for invalid input (bad size, wrong device) — never silently folded into backpressure
  • Returns false (not an error) only when every slot is busy

encode(..., commit:)

  • GPU-resident, no CPU readback at all
  • Same validation + backpressure contract as submit()
  • Slot releases on the buffer's actual GPU completion, not a CPU wait

Validation, every entry point

  • Input buffer length checked against the tensor's required bytes
  • Each output buffer length checked individually
  • Command buffer's device checked against the model's device
  • All of it throws — a wrong-sized buffer is a programmer error, not transient state

The split matters: an invalid call is a bug, surfaced immediately. Backpressure is expected, recoverable state — a dropped frame, not an exception.

4What every Fabric node built on one must do

DO Encode async work onto Fabric's shared per-frame commandBuffer, pass commit: false.

The work sits encoded, in order, alongside every other node's work, until Satin's own render layer commits the whole frame once. Same-buffer encode order is what makes this safe against upstream read/write races — no cross-buffer commit-order reasoning needed.

DO For a synchronous result, create a dedicated buffer this call owns exclusively and pass commit: true.

The package commits it internally (via its wrapper) as part of that call. The node's only remaining job is targetBuffer.waitUntilCompleted() — never an explicit .commit().

NEVER Call .commit() on a raw MTLCommandBuffer from node code. Full stop.

Not the shared buffer (not yours to commit) and not a dedicated one either (§2 — you can't know if it's already committed). If you need a buffer committed, ask the package to do it via commit: true.

DO Keep lifetime capture on completion handlers for anything the texture cache might recycle.

commandBuffer.addCompletedHandler { [weak self, image] _ in withExtendedLifetime(image) {} } — GraphRendererTextureCache recycles a managed image the instant its last Swift reference drops, with no regard for whether the GPU is still using it.

5Sync vs. async — the real tradeoff

Not a preference — a real, named cost either way. Pick deliberately.

Async (default, commit: false)

  • Zero CPU wait, no pipeline bubble
  • Steady-state one frame of latency on the numeric result
  • Inference slot only releases once the whole frame's shared buffer completes — under heavy per-frame GPU load, slots can starve, causing irregular, not just delayed, updates

Synchronous (commit: true, dedicated buffer)

  • Same-frame numeric result, no latency
  • Real, bounded CPU stall (this model's own GPU time — sub-millisecond for these models)
  • Slot releases fast, tied only to this node's own small buffer — no frame-load interference

Currently a compile-time flag per node (private static let synchronousInference = false) — not a port — until Fabric has a systemized protocol for per-node sync/async execution. Iterator usage forces synchronous = true unconditionally: each iteration needs its result before the next one runs, which the async path structurally cannot deliver in time.

6API symmetry between packages

MPS-ZipDepth and MPS-MediaPipe match on every point above. The one deliberate difference: outputBuffer: (singular) in ZipDepth vs. outputBuffers: [MTLBuffer] in MediaPipe — not an inconsistency, just each model's real tensor count (one output vs. several). Forcing ZipDepth into an array-of-one would be ceremony with no benefit.
